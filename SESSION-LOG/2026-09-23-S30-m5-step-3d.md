## 1. What was actually missing

Three specific gaps, each with its own tell in the existing code:

- **OTP delivery** (`portal/backend/app/api/auth.py`) — a literal
  `# TODO(M5 Step 3d): hand to the email sender` next to
  `log.info("otp issued (delivery not yet wired)")`. `otp.request_otp`
  already generated a real code; nothing sent it anywhere.
- **Virus scanning** — `inbound.client_uploads.scan_status` defaults to
  `'Pending'` and `server/src/main.rs::pull` already filters
  `WHERE scan_status = 'Clean'` before offering an upload to the desktop.
  Nothing ever moved a row out of `Pending`, so no client upload could
  reach an attorney no matter how long it sat in the queue.
- **Object storage** — `upload_document` computed a `sha256` and an
  `object_key` (`quarantine/{client_id}/{upload_id}`) and then discarded
  the bytes; the comment said so directly: "the row is created either way,
  so nothing a client sends is silently dropped — it sits Pending until
  the storage leg exists." And on the server side, `POST /sync/documents`,
  `DELETE /sync/documents/{key}` and `GET /sync/uploads/{id}/object` —
  named in spec §12 — did not exist as routes at all.

## 2. OTP delivery (`portal/backend/app/email.py`)

Real SMTP via stdlib `smtplib`, run off the event loop with
`asyncio.to_thread` since `smtplib` is synchronous. STARTTLS-capable,
AUTH-capable, all driven by five new settings (`smtp_host` and siblings) —
`smtp_host: str | None = None` is the "not configured" state, matching the
existing `expose_otp_for_tests` escape hatch rather than fighting it.

Wired into `api/auth.py::request_otp`: the 202 response no longer waits on
whether delivery succeeds. It can't — a slow or failing relay must not
become a timing oracle for the account-enumeration defence spec §15.11
already established. Failure is logged, never raised.

**Tested against a real SMTP server**, not a mock: `tests/test_email.py`
implements just enough of RFC 5321 (raw sockets, EHLO/AUTH/MAIL FROM/RCPT
TO/DATA) for `smtplib` to complete a real send over loopback. Five tests:
unconfigured returns `False`, a real plaintext send round-trips the code
and the correct addresses, AUTH PLAIN negotiates correctly when
credentials are configured, an unreachable relay and a relay that
rejects the message both come back `False` rather than raising.

## 3. Virus scanning (`portal/backend/app/scanning.py`)

Speaks clamd's `INSTREAM` protocol directly over TCP with `asyncio`
streams: a null-terminated `zINSTREAM` command, the payload as
four-byte-length-prefixed chunks ending in a zero-length chunk, then a
single verdict line. `scan_bytes` returns `None` — not `Failed` — when no
scanner is configured, so the caller can tell "not attempted" apart from
"attempted and something went wrong," and leave `scan_status` at its
`Pending` default in the first case rather than writing a verdict that was
never actually reached.

Wired into `upload_document`, after the object-storage write (§4) and
inside the same transaction as the insert. Since `portal_writer` had only
ever been granted `SELECT, INSERT` on `inbound.client_uploads` (S14,
0002_rls.sql, deliberately — the portal must not be able to rewrite an
upload once filed), a new migration was needed:

```
server/migrations/0005_scan_result.sql
    GRANT UPDATE (scan_status) ON inbound.client_uploads TO portal_writer;
    CREATE POLICY client_isolation_scan_update ... FOR UPDATE ...
```

One column, RLS-scoped like everything else — `status`, `object_key`,
`sha256` and the rest stay update-only by `sync_writer` (the desktop is
still the only actor that moves an upload to Ingested or Rejected).

**Tested against a real clamd protocol implementation**: `tests/test_scanning.py`
builds a from-scratch fake clamd (raw sockets) that reads the chunked
stream to completion — proving the framing, not just that a canned
response parses — before replying with a fixed verdict. Seven tests,
including the real EICAR test string reported Infected, a payload spanning
several chunks, an unreachable daemon and a dropped connection both
reported Failed (never Clean), and a negative control on the `FOUND`
detector.

## 4. Object storage — two languages, the same design

`portal/backend/app/object_store.py` and `server/src/object_store.rs` each
hand-roll a minimal S3-compatible client: AWS Signature Version 4,
path-style addressing (`<endpoint>/<bucket>/<key>`, no bucket-specific DNS
needed). `storage.py` already hand-rolls the *download* side (a custom
HMAC the edge verifies before proxying to the real bucket); these are the
matching upload side, signed the way the bucket itself actually requires.

Both are config-gated the same way ClamAV is: unset means "not configured"
— `put_object` returns `False` in Python, `ObjectStore::from_env()` returns
`Ok(None)` in Rust, and the callers skip the write rather than erroring.
*Partially* configured (some but not all five S3_* variables) is a hard
error in both — a half-configured bucket that looks live and silently
isn't is worse than refusing to start.

**Python side:** wired into `upload_document`. The PUT happens *before*
the database insert — a row naming an object nothing wrote is worse than
refusing the upload outright, since the desktop would later find nothing
at that key. A configured store that refuses the write now surfaces as a
503, not a silently-phantom row.

**Rust side:** three new routes on the sync server (spec §12, previously
unbuilt):

| Route | Purpose |
|---|---|
| `POST /sync/documents?key=<key>` | Store a shared document's bytes; the desktop computes the key itself (`documents/{client_id}/{document_id}`), so a re-share overwrites cleanly |
| `DELETE /sync/documents/{key}` | Remove on unshare; deleting an already-gone key is not an error, so a retried unshare is safe |
| `GET /sync/uploads/{id}/object` | The desktop downloads a quarantined upload to verify/ingest/refuse — only `status = 'Pending'` rows are servable |

**The other half of "share a document."** Wiring the PUT route exposed a
second, pre-existing gap: `mirror.documents_shared` has had an
`object_key` column since S14, but `apply()` in `main.rs` had no upsert
case for `entity_type = "Document"` — only its tombstone `Delete` existed
(`delete_entity` already handled it; `upsert_document` didn't). Without
it, the object-storage route this session adds would have nothing to
connect to — bytes in the bucket with no metadata row ever pointing at
them. Added `DocumentPublic` (`types.rs`) and `mirror::upsert_document`,
matching the existing upsert pattern exactly (`ON CONFLICT (id) DO UPDATE`).

**Tested with independent signature verification**, in both languages:
each fake bucket doesn't just check that an `Authorization` header is
present — it recomputes the SigV4 signature itself, the same algorithm
written a second time, and rejects anything that doesn't match. A wrong
secret is proven to get a real `403`, not merely asserted to. Python:
4 tests. Rust: 8 unit tests on `object_store.rs` (from_env validation,
put/get/delete round trips, wrong-secret rejection, special-character
key encoding) plus 6 route-level integration tests on `main.rs` (upload→
delete round trip, missing-token refusal, 503 when unconfigured,
pending-upload download, 404 on an already-ingested upload, and the
`Document` push landing in the mirror with its object key).

A discovered, related, out-of-scope gap: `apply()` still has no upsert for
`Payment` or `Notification` either, even though `delete_entity` already
handles both. Documented in `server/SCHEMA.md`; not fixed here, since it
has nothing to do with object storage, scanning, or OTP.
