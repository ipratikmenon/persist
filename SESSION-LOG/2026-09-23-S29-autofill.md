## 1. What was actually missing

Every shipped manifest has declared `autofill` sources since S20 —
`client.name`, `matter.responsibleAttorney`, `matter.forum`,
`ipAsset.applicationNumber`, `ipAsset.title`, `ipAsset.classes` — and nothing
had ever read them. `tm-examination-reply` declares six; `legal-notice`
declares one (`CLIENT_NAME`). The Smart Form Compiler's whole premise — an
attorney drafts a filing without retyping what the firm already has on file —
was half-built: the schema said where the values lived, and nothing went and
got them.

---

## 2. What the sources resolve against

Before writing anything I read the actual query layer rather than guess what
was available: `db/queries/matters.rs` already had `responsible_attorney_name`
(returns a name, explicitly never an id — its own doc comment says so) and
`get_client_row`; `db/queries/ip_assets.rs` had `list_by_matter` and `get`. All
the plumbing this needed already existed one layer down; nothing had called
it for this purpose.

`services/autofill.rs::resolve(pool, declared, matter_id, ip_asset_id)` walks
the declared `(field key, source)` pairs once, caching each of client name,
attorney name and the resolved IP asset so a manifest naming `client.name`
three times does not cost three queries.

**`ipAsset.*` sources need to know which asset**, and the manifest doesn't say.
Resolution: use the one named, if given; otherwise, if the matter has exactly
one IP asset, use that (a trademark matter usually is about one mark); with
zero or several, resolve nothing rather than guess. Wrong in that guess and it
is a wrong mark on a Registry filing — the empty field the attorney has to fill
in either way is the safer failure.

**A source that cannot be resolved is left out of the map, not bound to an
empty string.** This mattered enough to write two separate tests for: an empty
`classes` array (guarded early, in `ip_asset_field`) and a `forum` column
holding `''` rather than `NULL` — SQLite does not stop you doing that, and
without the late filter it would have overwritten a field with a value that
merely looks resolved.

## 3. The command, and the Deck side

`resolve_autofill(templateId, matterId, ipAssetId?)` — behind the same
permission as `render_document`, since this reads the client's name and the
matter's details, which is not public the way a template's shape is. The
command itself is thin, matching how `render_document` and the rest of this
file are structured: real logic in the service, the wrapper just plumbs
`AppState` through. The one piece of logic in the command file —
`declared_autofill`, extracting `(key, source)` pairs off a manifest — got its
own test against the real shipped `tm-examination-reply.json`, because it's the
one part of `resolve_autofill` that isn't `autofill::resolve` itself and so the
one part that could actually be wrong without a test catching it.

Deck: one `useEffect` in `SmartForm.tsx`, keyed on `[manifest, matterId,
ipAssetId]`, that calls `resolveAutofill` once and merges the result into
`values` — but only into a key that is currently `undefined`. It cannot
overwrite a field the attorney has already typed into, field by field, not by
gating the whole effect on "has the form been touched." A failure is swallowed
silently: autofill is a convenience the record offers, not a step drafting
depends on, and a matter with nothing to offer should look no different from a
failed lookup.

Also added: an optional `?ipAsset=` URL parameter, for the day something links
into the Smart Form already knowing which mark. Nothing currently sets it —
the "matter's only asset" default is what carries the common case today.

## 4. Verified past the unit tests

11 tests in `services/autofill.rs`, 2 more in `commands/drafting.rs` — but
unit tests prove the resolver returns the right map, not that Deck actually
shows a pre-filled field. Added a mock fixture and a new screenshot,
`24-smart-form-autofilled`: opens the Reply to Examination Report against a
matter fixture, types nothing, and captures it. The six declared fields —
signing attorney, registry office, application number, mark, class, applicant —
come back filled from the mock's `resolve_autofill`; the two date fields, which
declare no autofill source, are correctly blank. That is the thing worth
seeing rather than trusting: the wiring from Rust command through the React
effect through to the rendered input actually connects.

---

## 5. Negative controls, and one that needed a second attempt

Removed the "skip empty values" guard (`.filter(|v| !v.is_empty())`) and ran
the suite expecting the empty-class-list test to catch it. It didn't — that
test exercises a different, earlier guard inside `ip_asset_field`, which
already returns `None` before the value ever reaches the later filter. The
control passing when it should have failed is itself a finding: a test can
look like it covers something and cover something adjacent instead.

Wrote a second, more targeted test — seed a matter with `forum` stored as an
empty string rather than `NULL` (a distinction SQLite does not enforce) — and
re-ran the same control. That one failed exactly as expected, confirming the
late filter is doing real, independent work and now has a test that actually
proves it.
